# Project: The Pulp Doctor — MERN Full-Stack Endodontist Website

Build a complete, premium, responsive, production-oriented full-stack website for **Dr Charu Makhija**, professionally known as **The Pulp Doctor**. This is a real client project. Do not build only a static landing page or UI prototype. Implement the frontend, backend, MongoDB database, authentication, appointment booking, admin dashboard, dentist referral workflow, secure file uploads, and email notifications.

## 1. Technology Stack

Use the MERN stack:

- **Frontend:** React + TypeScript + Vite
- **Styling:** Tailwind CSS
- **Routing:** React Router
- **Backend:** Node.js + Express.js + TypeScript
- **Database:** MongoDB Atlas + Mongoose
- **Authentication:** JWT-based authentication using secure HTTP-only cookies, bcrypt password hashing, and role-based authorization
- **Calendar:** Custom appointment calendar with date selection and live availability; FullCalendar may be used for the admin calendar
- **Email:** Nodemailer with a verified SMTP provider, or Resend through a server-side integration
- **File storage:** Private Cloudinary storage or private S3-compatible storage for referral attachments
- **Validation:** Zod or an equivalent validation library on the frontend and backend
- **Version control:** GitHub

Use current stable, compatible dependencies. Keep the frontend and backend in separate directories:

- `client/`
- `server/`

Create a complete `.env.example`, API documentation, MongoDB models, reusable React components, middleware, controllers, routes, services, and error handling.

Do not use Supabase, Firebase, or another database/authentication platform. MongoDB Atlas must be the primary database.

## 6. Appointment Booking System

Build a real, database-backed booking engine.

Initial slot duration: 60 minutes.

Generate eight slots for an ordinary 11 AM–7 PM clinic day:

- 11 AM–12 PM
- 12 PM–1 PM
- 1 PM–2 PM
- 2 PM–3 PM
- 3 PM–4 PM
- 4 PM–5 PM
- 5 PM–6 PM
- 6 PM–7 PM

Patient workflow:

1. Select clinic/location.
2. Select a date.
3. Fetch the correct schedule and live availability from Express APIs.
4. Select an available slot.
5. Enter patient name, phone, email, appointment type, and optional notes.
6. Review and submit.
7. Receive confirmation only after the server successfully creates the booking.

Booking requirements:

- Display only valid, published slots.
- Never reveal another patient's information.
- Mark online bookings unavailable immediately after successful creation.
- Support bookings made by phone through the admin dashboard.
- Online and phone bookings must use the same backend availability checks.
- Prevent double booking, including concurrent requests.
- Use MongoDB transactions where supported and appropriate, plus atomic reservation logic and unique constraints or equivalent concurrency protection. Do not rely only on a frontend check.
- Validate request data on the server.
- Handle loading, empty, error, retry, cancellation, and rescheduling states.
- Do not confirm a booking if the database operation fails.
- Do not silently delete existing appointments when schedules change.
- Support configurable cancellation and rescheduling rules.

Suggested endpoints:

- `GET /api/availability?locationId=...&date=...`
- `POST /api/appointments`
- `GET /api/appointments/:id`
- `POST /api/appointments/:id/cancel`
- `POST /api/appointments/:id/reschedule`

Protect private appointment details with authorization.

## 11. Security Requirements

- Use MongoDB Atlas with restricted network access and a least-privilege database user.
- Hash passwords using bcrypt or an appropriate password-hashing implementation.
- Use short-lived JWT access credentials and secure HTTP-only cookies; configure CSRF protections where required by the chosen cookie architecture.
- Implement role-based access control on the backend.
- Validate and sanitize incoming requests.
- Use rate limiting, secure headers, CORS allowlists, and spam protection.
- Keep secrets in environment variables.
- Never expose MongoDB credentials or JWT secrets to React.
- Restrict uploads by content type, file size, and allowed extensions.
- Store referral attachments privately.
- Avoid sensitive clinical data in public logs, analytics, and URLs.
- Implement access, retention, and deletion procedures for sensitive records.
- Add privacy and consent wording placeholders for the doctor to approve.
- Protect against NoSQL injection and unsafe file uploads.
